## Headline conclusions

1. **The reference `activity-shell` entry script silently swallows cancellation, and the fix is not `exec`.** Measured on a native Linux daemon with `--init`: the design's exact script shape exits **143 in 143 ms** with the workload's SIGTERM trap never firing and `values.json` never written. Plain `exec` (rule 2 literal) delivers the signal but then **nothing can write `values.json`** — so rule 2 as written is *unfollowable* for any activity that must produce a result. Only `child & trap … TERM; wait` satisfies both. §10.1 rule 2 needs an explicit exception, not a script patch.
2. **Container exit codes 125/126/127 carry no runtime guarantee.** Measured: a workload choosing `exit 126` produces `.State.ExitCode == 126`, byte-identical to the CLI's own diagnostic. §8.2 would permanently refuse to retry a shell script whose last command was not found — which POSIX makes the *normal* meaning of 127. AGENTS.md:115-117 forbids exactly this. The distinguishing signal exists at a different layer and the `ContainerRuntime` interface already has the right shape for it.
3. **`buf breaking` reports two complaints, not one.** Reproduced end to end by extracting §2.2 and applying §2.3's four patches: `orkflow.proto:21:1` *and* `run.proto:12:1`. `buf build` and `buf lint` pass clean; `WIRE_JSON` and `FILE`-minus-`FIELD_NO_DELETE` both pass. The compatibility *conclusion* survives; §2.1 and §14.6 understate their own measurement because §14.6's transcript predates the `run.proto` patch §2.3 now specifies.
4. **A HEAD-only resolver cannot populate `ImageRef.platforms`, which the canonical digest hashes.** HTTP forbids a body on HEAD; the child `manifests[]` array requires a GET. Two conforming resolvers would mint different definition digests for the same index. This is an internal contradiction between §4.3 step 2 and §4.4's canonical field list at line 959-961.
5. **`RunPlan.Limits` cannot mean what it says.** `internal/engine/pools.go:410-436` builds `routes` as a *map of many pools to many queues* and a `tasksByPool` index — one run genuinely spans pools with different Orker-local caps. A single submit-time value cannot represent that, and `internal/api` does not own worker-local policy.
6. **The required proto field name is free.** `SubmitRunRequest.idempotency_key = 4` is a different message (`service.proto:210`), and the Go claim path uses a bare `key string` (`internal/engine/idempotency.go:82-122`, `claim.go:82`) with no `IdempotencyKey` identifier at all. Naming `ExecuteTaskInput.idempotency_key` costs nothing and makes the wire JSON (`idempotencyKey`) identical to the `task.json` key the workspace already writes.
7. **Phase 2 is not disjoint from Phase 1 or 3, as written.** §11.2 owns `pkg/artifacts` + the engine read side, but its bullets assign the §5.4 sequence, adoption, the seven-field identity check, the undecodable branch and 412 handling — all inside `internal/orker.OCIDispatcher`, which §11.1 owns — plus "the UI", which §11.3 owns.

Round 2's fixes landed and hold: `values_json` is now `bytes` with the four measured `Struct` losses documented (§2.2:307-318); `CommitRef.sha256` carries the never-re-marshal rule (:279-284); `commit_max_bytes` replaced the 64 KiB cap; `RunPlan.CommitRoot` moved URI composition out of workflow code (§5.2:1125-1153); `link(2)` replaced `O_EXCL`-at-final-path; content-addressed S3 output keys close the overwrite race (§5.4:1325-1341); `resolved_at` was removed from `ImageRef`; `canonicalOrkflow` replaced `Deterministic:true` (§4.4:937-963); `run.proto` got a full patch.

## New measurements this session

### M1 — SIGTERM through `--init`: the design's script, and the two candidate fixes

Native Linux daemon (`docker version` → `linux/amd64 29.1.5`; `docker info` → `Ubuntu 24.04.2 LTS`, `seccomp,profile=builtin`). Workload traps TERM, prints, exits 0. `docker stop --timeout 5`.

| Case | stop took | exit | logs |
|---|---:|---:|---|
| **(a) design as written** — `sh -c "$cmd"`; `rc=$?`; write values; `exit $rc` | 143 ms | **143** | `WORKLOAD-UP` |
| **(b) `child & trap 'kill -TERM $child' TERM; wait`** | 204 ms | **0** | `WORKLOAD-UP \| WORKLOAD-GOT-SIGTERM \| ENTRY-WROTE-VALUES rc=0` |
| **(c) `exec sh -c "$cmd"`** (rule 2 literal) | 221 ms | **0** | `WORKLOAD-UP \| WORKLOAD-GOT-SIGTERM` |

Reading:

- **(a) fails both halves.** The workload's handler never ran and `values.json` was never written. Exit 143 = 128+15: `--init` forwards SIGTERM to its *direct child only* — tini defaults to signalling one child and Docker injects `docker-init -- command` without `-g` ([tini README](https://github.com/krallin/tini/blob/369448a167e8b3da4ca5bca0b3307500c3371828/README.md#L193-L215), [Moby `oci_linux.go`](https://github.com/moby/moby/blob/40baece19edb76aad9f1db0c1e615a59c19f3c01/daemon/oci_linux.go#L726-L744)) — so `entry.sh`, a `sh` with no trap, dies on default disposition and the grandchild is torn down with it. **Not** the "degrades to SIGKILL at the grace boundary" the finding predicted; it is faster and more total. §10.3's own assertion "SIGTERM is honored within the grace period" fails for the platform's own reference image.
- **(c) proves rule 2 is unfollowable.** `exec` replaces the shell ([bash manual](https://www.gnu.org/software/bash/manual/html_node/Bourne-Shell-Builtins.html#index-exec)), so nothing after it can write `values.json` → `ContractViolation/VALUES_MISSING` on *every* successful run.
- **(b) is the only shape that satisfies the contract.** Caveat for the spec: a trapped signal makes `wait` return >128 immediately ([POSIX §2.12](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html#tag_19_12)), so the child's real status needs a second `wait` on that path only — an unconditional double-`wait` loses the status when no signal arrived.

**Resolution:** §10.1 rule 2 needs an explicit exception — "an entry script that must produce `values.json` after the workload exits MUST run it in the background, install a TERM trap that forwards to `$!`, and `wait`; `exec` is required only when the script hands off and produces nothing itself" — plus the corrected script in §10.2 and a `orkstack activity test` assertion that the workload observes SIGTERM.

### M2 — Exit codes 125/126/127 are not reserved

```
workload exit 125 -> docker reports 125   logs=WORKLOAD-CHOSE-125
workload exit 126 -> docker reports 126   logs=WORKLOAD-CHOSE-126
workload exit 127 -> docker reports 127   logs=WORKLOAD-CHOSE-127
workload exit  42 -> docker reports  42

contrast: docker run CLI status, missing entrypoint = 127
contrast: docker run CLI status, daemon refusal     = 125
```

A started container's status passes through verbatim. POSIX makes 127 the shell's own "command not found" and 126 "not executable" ([§2.8.2](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html#tag_19_08_02)), so a *routine* `activity-shell` failure lands on 127 and §8.2:1635 would classify it `ContractViolation/CONTAINER_COMMAND_NOT_FOUND`, **never retried**. AGENTS.md:115-117: *"Any non-zero exit means the activity failed. Retry behavior belongs to Temporal workflow policy, not magic exit codes."*

**Resolution, and it is clean:** the signal that actually distinguishes the two lives at a different layer, and §6.1's `ContainerRuntime` already has the shape. `Create` and `Start` return `error`; `Wait` returns `(ExitStatus, error)`. A container that never started never reaches `Wait`, so:
- `Create`/`Start` error → `InfrastructureError/RUNTIME_REFUSED` (retryable) or `WORKSPACE_NOT_BINDABLE`, from the runtime error, not a number.
- Every `Wait` non-zero → `ActivityFailed/CONTAINER_EXIT_NONZERO`, retried per the task's policy.
Delete `CONTAINER_NOT_EXECUTABLE` and `CONTAINER_COMMAND_NOT_FOUND`; keep `RUNTIME_REFUSED` but source it from the runtime error. This removes a deviation from AGENTS.md rather than needing one recorded in §13.

Against the code: `internal/dsl/compile.go:121-193` must stay pure (§4.3:900-904 is right about this), `hash.go`'s `sourceHash` is superseded by `canonicalOrkflow` for the *definition digest* but the round-2 question of **where a derived `version:` is assigned** is now answered by §4.4 — worth re-checking that `pkg/artifacts/orkflow_store.go:400-408`'s `sameStoredOrkflow` (which compares `SourceYaml` first, then `proto.Equal` with only `CreatedAt` cleared) agrees with the new canonical field set; with `resolved_at` removed from `ImageRef` it now can, which is a round-2 finding the current draft closed.

**3. Commit protocol completeness.** Adoption result shape: choose (i) refetch+verify or (ii) never-inline, explicitly (F08/F24 row). Undecodable branch: an **in-attempt reread** removes the need for any durable carrier, and `link(2)` makes the branch unreachable for torn writes once Phase 2 lands (F07/F17 row). The first-read error, if a cross-attempt rule is kept anyway, must be a new retryable `InfrastructureError/COMMIT_UNDECODABLE_RETRY`; §8.2 currently has none.

**4. Lifecycle and timeout budget.** A data-dependent Start-to-Close with a short Heartbeat timeout, per Temporal's own long-running-activity guidance; the fixed 120 s is unsupported and interacts badly with the `MaximumAttempts: 1` default (F06/F19 row). Failure-path scan: run §3.5's rules plus readability before uploading, without displacing the workload's error (F02 row).

**5. Error categories.** Yes, it conflicts with AGENTS.md §3.2, and the codes are measurably ambiguous (M2). Every observed non-zero `Wait` status → `ActivityFailed`; start failures arrive as `ContainerRuntime` errors.

**6. Limits ownership.** No — `RunPlan.Limits` cannot hold post-policy effective values. Split contract limits (deployment-wide, engine-owned, on the wire) from resource policy (Orker-applied, written into `task.json`), which is already how §3.2 describes `resources.*` (F10 row).

**7. Runtime surface.** `LoadLayout` on `ContainerRuntime` plus `ImageRef.delivery`; state which layer verifies the child manifest and the layer blobs (F12/F16 row). Survivors under `OCIDispatcher` — verified against the code and correctly stated in §6.2:1433-1440: `resolver.go:23-151` (staging + `safeComponent`), `render.go:36-168` (`with:` → `config.json`), `logsink.go:54-521` unchanged, `linewriter.go` moving to `pkg/logstream`, `activity.go:252-268` (per-attempt workdir + `defer RemoveAll`), and the two load-bearing behaviours at `activity.go:115-123` (sink opens first, closes before return) and `:155-171` (a failed activity still publishes, and a storage error never replaces the workload's). `registry.go` dies with `BuiltinRegistry`.

**8. First-party activity contract.** Neither — measured (M1): SIGTERM does **not** reach the workload, and the container exits 143 in 143 ms rather than degrading to SIGKILL at the grace boundary. The fix is a TERM trap forwarding to `$!` plus `wait` (with the second `wait` on the signal path only); `exec` is correct for rule 2's stated purpose but incompatible with writing `values.json`. Cross-check against `pkg/plugins/shell/shell.go:183-201`: today's in-process shell plugin has the same structure — it runs the command as a child and collects `exit_code` afterwards — so this is a property the migration inherits, not one it introduces.

**9. Phase boundaries.** Freeze `artifacts.CommitStore` as an interface in Phase 1 with its `OCIDispatcher` call sites; Phase 2 owns only implementations behind it plus the engine category read side; move the UI work to Phase 3 (F05/F21 row).
