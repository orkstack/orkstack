# Changelog

Every change that may affect the people who run or use OrkStack is recorded
here. The format follows
[Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and versions
follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Each
breaking change is marked **BREAKING**.

Such a change lands with its entry under `[Unreleased]`, saying what they must
do about it, if anything; a change that cannot affect them, such as a
documentation or test change, has none. At a release that section becomes the
version's own, and its text is the release's notes on GitHub, word for word.

## [Unreleased]

## [0.2.0] - 2026-11-05

### Added

- An Orker now cordons itself during an object storage outage, so tasks wait in the pool instead of using up their retries, and resumes by itself once the store answers; `ORK_ORKER_STORE_CHECK_ENABLED=false` turns it off. `cordoned` is true for either cause while `cordon_reason` stays the operator's alone, so a client that shows why an Orker is cordoned should also read `ListOrkers`' new `store_outage` ([DEPLOY.md, "When object storage goes away"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#when-object-storage-goes-away)).
- `orkctl stats --by day` and `--by hour` count the runs created per day or per hour on your own calendar, and `GetStats` takes `bucket_width`, `timezone` and `bucket_count` for the same series ([CLI.md, "`orkctl stats`"](https://github.com/orkstack/orkstack/blob/main/docs/CLI.md#orkctl-stats)).
- A task waiting on a pool whose every Orker is at its declared capacity now says so, on the run page, in `orkctl run inspect` and in `InspectRun`'s `LiveAttempt.capacity_wait`. With metrics on, an Orker that declares a capacity also reports `ork.orker.capacity.*` and `ork.orker.admission.*`, and one that declares none logs at boot that its admission is best effort ([DEPLOY.md, "Declaring an Orker's capacity"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#declaring-an-orkers-capacity)).
- A canceled run shows who canceled it: the name your gateway asserted in `Ork-Principal` (`ORK_PRINCIPAL` for `orkctl`), as `canceled_by` in the API, in `orkctl run get` and `run list` and on the run page, always marked asserted and never authenticated. A cancel without the header, and a run canceled before this release, show no name.
- Activity images can carry an icon and descriptions of themselves, their ops and their keys: add `icon:` and `description:` to `interface.ork.yaml` and build with this release's `orkctl`, because an earlier one refuses those keys ([ACTIVITY_IMAGES.md, "Describing the activity"](https://github.com/orkstack/orkstack/blob/main/docs/ACTIVITY_IMAGES.md#describing-the-activity)). `orkctl activity inspect`, `ListActivities` and `InspectActivity` show them, and `InspectActivity` can answer a reference pinned by digest from an earlier read (`allow_cached`).
- `orkctl activity test` now reports the `with:` interface an image declares (declared, none or malformed), in its table and in `--json`; it never changes the verdict.
- The image policy also verifies cosign 3's default signature format, a Sigstore bundle stored as an OCI referrer, beside the legacy `.sig` layout, so you can sign your own images with cosign 2 or 3 ([DEPLOY.md, "Image supply-chain policy"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#image-supply-chain-policy)).
- Each release's page now ends with every image's digest and the commands that verify them, and the release attaches `SHA256SUMS.sigstore.json`, cosign's bundle of the checksum signature, beside `SHA256SUMS.sig` ([UPGRADING.md, "Release artifacts"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#release-artifacts)).
- The API listener now bounds what a client may make it hold: 64 KiB of headers (`431` above that), sent within 10 s over HTTP/1.1, `ORK_HTTP_IDLE_TIMEOUT` (15 minutes) for an idle connection, and `ORK_REQUEST_MAX_BYTES` for one Connect message (`resource_exhausted` above it). Unset, that cap follows the task ceiling, and a value set below that is refused at boot; the admin listener has the same kinds of bound ([DEPLOY.md, "The API listener's bounds"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#the-api-listeners-bounds)).

### Changed

- **BREAKING** No secret floor admits an Orker's own sources any more, an empty `ORK_ORKER_SECRET_ALLOW` included: a task that names one (such as `env:ORK_*`, `env:OTEL_*`, `env:AWS_*`, `file:/proc/...`, `file:/run/secrets/...`, or a file under its work root, the temp directory when `ORK_ORKER_WORKDIR` is unset) fails `SECRET_NOT_PERMITTED`, and a floor entry that can match only such sources stops the Orker at boot. Before you upgrade, give each such task a source of its own, set `ORK_ORKER_SECRET_ALLOW` on every Orker to exactly those sources, and drop any such entry ([UPGRADING.md, "The Orker's secret floor"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#the-orkers-secret-floor)).
- **BREAKING** A `file:` secret source must be a plain absolute path, with no `..`, `.` or empty segment, of at most 4096 bytes, under every floor, the empty one included; any other name fails `SECRET_NOT_PERMITTED`. Write each such source's path out plainly ([UPGRADING.md, "`file:` secret sources"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#file-secret-sources)).
- **BREAKING** The API listener now answers `403` to a request whose `Host` it does not admit, which stops DNS rebinding through a public name. Set `ORK_ALLOWED_HOSTS` on every `ork` to each name with a dot the engine is reached by; an IP address, `localhost`, a name with no dot and the host `ORK_HTTP_ADDR` names need nothing ([UPGRADING.md, "Allowed hosts"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#allowed-hosts)).
- **BREAKING** The admin listener (`ORK_ADMIN_ADDR`, on `ork` and `orker`) applies the same rule. List in `ORK_ADMIN_ALLOWED_HOSTS` each name with a dot a scraper dials, such as a Prometheus static target `host.docker.internal` or a Kubernetes Service FQDN; a scraper that dials an IP address needs nothing ([UPGRADING.md, "Allowed hosts"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#allowed-hosts)).
- **BREAKING** The release signs its images and `SHA256SUMS` in cosign 3's bundle format, which an engine or Orker of v0.1.0 cannot read: where a run's namespace requires a signer, a v0.1.0 Orker still polling refuses its bundle-signed images with `IMAGE_NOT_SIGNED`, which is never retried. Upgrade the Orkers with the engines; a deployment that stays on v0.1.0 is unaffected by this release, which leaves the `0.1` tag its catalog names on v0.1.0's images ([UPGRADING.md, "Release artifacts"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#release-artifacts)).
- **BREAKING** The Temporal Go SDK 1.50 records a marker in a run's history the first time one cancellation reaches more than one of its open scopes, which an engine of 0.1.0 cannot replay, so on a rollback or in a fleet that mixes releases such a run stays `RUNNING` (`unknown SDK flag: 9`) until an engine of 0.2.0 picks it up. With versioning on, roll back as before; with versioning off, roll back below 0.2.0 only when no run is open, and replace every engine replica together when rolling forward ([DEPLOY.md, "4. Rolling back"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#4-rolling-back)).
- **BREAKING** Every first-party activity image now ships jq 1.8 (was 1.7) and BusyBox 1.37, the `git` image git 2.54 and the `http` image curl 8.23, and jq 1.8 changes what some filters compute in a `json` task and in any `jq` a `shell` task runs. Check those filters and commands before you next apply their Orkflows ([UPGRADING.md, "jq 1.8 in the first-party images"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#jq-18-in-the-first-party-images)).
- **BREAKING** The `template` image now renders with gomplate 5.3.1 (was 4.3.3), which removed most of the names gomplate 4 served with a deprecation warning, so a template that calls one fails to render. Replace them, and check any `GOMPLATE_CONFIG` file and `AWS_META_ENDPOINT` setting, before you next apply those Orkflows ([UPGRADING.md, "gomplate 5 in the `template` image"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#gomplate-5-in-the-template-image)).
- **BREAKING** The Orker's boot probe now runs `docker.io/library/alpine:3.24` by digest (was alpine 3.20), and an Orker that cannot pull it refuses to start with `BIND_PROBE_IMAGE_UNAVAILABLE`. On an air-gapped or rate-limited host, mirror or load it before you upgrade ([UPGRADING.md, "One release at a time"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#one-release-at-a-time)).
- **BREAKING** An Orkflow whose `retry:` sets a negative `initial_interval_seconds` or `maximum_interval_seconds`, a `maximum_interval_seconds` below its `initial_interval_seconds`, or a `backoff_coefficient` that is set below 1 or not finite is now refused by validate, apply and plan, whatever its `maximum_attempts`. Fix the document before you next apply it; a version applied earlier keeps starting, with the nearest policy the cluster accepts ([UPGRADING.md, "Upgrading Orkflows with the release"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#upgrading-orkflows-with-the-release)).
- `uses: shell` and the other first-party names now resolve to the activity images' `0.2` tag when an Orkflow is applied, and a version already applied keeps the image it pinned. A host that mirrors the images needs the `0.2` images before that apply ([UPGRADING.md, "Upgrading from 0.1.0 to 0.2.0"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#upgrading-from-010-to-020)).
- A `retry:` that sets no `maximum_interval_seconds` now waits at most 60 seconds between attempts, not 100, in runs submitted from this release on. Set `maximum_interval_seconds: 100` to keep the old spacing ([UPGRADING.md, "Defaults that moved"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#defaults-that-moved)).
- Where the cluster has fair dispatch enabled, a run's requests for a pin host are now ordered by namespace as its tasks are, for runs submitted from this release on ([DEPLOY.md, "Fair dispatch across namespaces"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#fair-dispatch-across-namespaces)).
- An unknown key in an Orkflow or an activity interface is now refused in the document's own words, naming the key, where it stands and the keys allowed there (`line 10: unknown key "need" in tasks[1] of the Orkflow; allowed: …`). A script that matches the old sentence, which named an internal type, needs updating.
- Connect 1.21 gives some broken connections a different code, `canceled` or `internal` where a client saw `unavailable`, `invalid_argument` or `unknown`, and `orkctl run watch` and `run inspect --watch` now resume on a `canceled` they did not cause. A client that switches on these codes should check them ([UPGRADING.md, "Connect 1.21's error codes"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#connect-121s-error-codes)).
- The Temporal SDK's `temporal_activity_execution_failed` and `temporal_local_activity_execution_failed` metrics now carry a `failure_reason` attribute, and `temporal_sticky_cache_total_forced_eviction` no longer counts a worker's shutdown. A dashboard built on them may need adjusting.
- `CancelRun` now answers `UNAVAILABLE` or `RESOURCE_EXHAUSTED` when the cluster could not take the cancellation, and `CANCELED` or `DEADLINE_EXCEEDED` when the caller gave up first, instead of `INTERNAL`. A client may retry the first two.
- The web UI has a new design, Harbour: a light sidebar, Inter and JetBrains Mono type, and the OrkStack mark.
- The web UI's Runs page now opens with the last day's counts, which filter the list, and the last 7 days' outcomes, failures and flakiest tasks; a run page shows what changed since the last run, keeps one log and one card on the task you select, and lets you pause its updates without losing any; and the Orkflow editor shows the docs of the activity under the caret. A run page's `view=` parameter is gone, and in the UI cancelling a run asks for a reason and cordoning an Orker needs one.
- Every example in `examples/` now runs as it stands, with no inputs, given internet access, with three exceptions: `order-saga` and `approval-gate` still need `notify-block` stored first, and `custom-image` is now a recipe beside its build, gone from the Apply page's gallery. A store keeps any older version it holds, and if you adapted an example or submit one with your own inputs, some inputs and defaults changed ([UPGRADING.md, "The examples"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#the-examples)).
- The quickstart's Orker is now a pin host, one pin at a time, so an Orkflow with a pin runs on it with no setting of yours, and the quickstart runs Temporal's development server 1.9.1 and SeaweedFS 4.51.

### Removed

- Ten older examples are gone from `examples/` and from the Apply page's gallery: `advanced-demo`, `awaited-approval`, `branch-and-recover`, `cached-pipeline`, `composed-release`, `file-read`, `hello`, `pinned-build`, `release-block` and `shell-eval`. An Orkflow a deployment already stored from one of them is unaffected; for a new one, start from a [current example](https://github.com/orkstack/orkstack/blob/main/examples/README.md).

### Fixed

- A failed task's `error.message` now says the Orker's sentence once; it used to repeat it after the failure's category, usually marked `retryable: true` whatever the failure's own `retryable` said. A script that matches the repeated part needs updating.
- The quickstart's first start no longer stops with the Orker exited on a `403 AccessDenied`, which about half of first starts from clean volumes did. Running `docker compose up` twice is no longer needed.
- An Orker that cannot use its object store at boot now stops with the new `COMMIT_STORE_UNAVAILABLE` and the store's own answer; `COMMIT_STORE_NOT_CONDITIONAL` now means the store answered and cannot do conditional writes. An alert on the old reason for these causes needs the new one too ([REASONS.md](https://github.com/orkstack/orkstack/blob/main/docs/REASONS.md)).
- `GetStats` and `orkctl stats` no longer count a run twice, once as finished and once as running, in the moment after it ends.
- An Orker's own policy checks (its cpu and memory caps, secret schemes and `ORK_ORKER_SECRET_ALLOW` floor) now run after commit adoption and the memo step, so a retry another Orker already committed, or a cached task whose memo hits, no longer fails on an Orker with narrower settings. `RUN_AS_ORKER_UNAVAILABLE` is now raised with them, before secrets are staged and the image is pulled.
- `orkctl task run --secret NAME=file:PATH` now says why a file cannot be used, as the file system gave it, rather than calling every such file missing.
- The Orker's boot probe no longer leaves `ork-bindprobe-*` or `ork-sigprobe-*` containers behind when its boot is stopped or refused. One it could not remove, because it was killed first, carries the `ork.orker` label and is reaped by the next boot under the same identity.
- A task whose `retry:` sets an `initial_interval_seconds` above the default maximum interval, and no `maximum_interval_seconds`, no longer leaves its run stuck. On a deployment with versioning, a run v0.1.0 already left stuck stays on v0.1.0 and never gets the fix: cancel it, and terminate it if it stays running ([UPGRADING.md, "Upgrading Orkflows with the release"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#upgrading-orkflows-with-the-release)).
- Numbers a run used without publishing an event, because object storage refused its record, are now said rather than skipped, and a refused `RUN_CREATED` is written again under its number, so a stream no longer silently begins at sequence 2. Check any client that switches on event types for the new `STREAM_GAP`, which changes no run or task, and on errors for the `DataLoss` a read of the archive over such numbers ends with ([DEPLOY.md, "6. Replay safety across versions"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#6-replay-safety-across-versions)).
- A finished run that did not archive itself, because it was terminated from outside or object storage refused its ending, now gets an archive from a sweep on every `ork` replica instead of disappearing when the cluster's retention expires it. It is still lost if object storage is down at every pass until then, so alert on the new metric `ork.archive.sweep.unconfirmed` ([DEPLOY.md, "Retention cleanup and bucket lifecycle rules"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#retention-cleanup-and-bucket-lifecycle-rules)).

### Security

- Text an image or a registry supplies, in an image's `interface_error`, a resolution error or a signature check's refusal, is now escaped and cut at 512 bytes, and `orkctl --json` of commands such as `run get`, `run list`, `activity inspect` and `activity list` writes DEL, every C1 control and every format character as a `\u` escape, so neither can drive your terminal. The `--json` output decodes to the same values.
- The web UI's page is now sent under a strict content security policy, which the engine sends as a header: scripts run only from the page's own origin, inline ones only when the policy names their hash, and `eval` only for the YAML editor's schema checks. A script a proxy injects into the page is now blocked.
- The first-party activity images move to Alpine 3.24; Alpine 3.20, their base until now, is past its support window.
- The `template` image still carries go-jose v4.1.4 (GHSA-mgcc-cww5-fp2q, high, fixed in v4.1.6) inside gomplate 5.3.1, gomplate's latest release. There is nothing to do; it moves when gomplate releases with the fix ([the image's README](https://github.com/orkstack/orkstack/blob/main/images/activity-template/README.md)).
