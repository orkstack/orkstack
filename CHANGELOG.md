# Changelog

Every change that may affect the people who run or use OrkStack is recorded
here. The format follows
[Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and versions
follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Each
breaking change is marked **BREAKING**.

Such a change lands with its entry under `[Unreleased]`, saying what they must
do about it, if anything; a change that cannot affect them, such as a
documentation or test change, has none. At a release that section becomes the
version's own, and its text is the release's notes on GitHub, word for word.

## [Unreleased]

### Added

- An Orker's boot now logs a warning naming the containers of other Orker identities on its daemon, which may be left by an Orker that never returned and run with no time limit. It stops and removes nothing, because another Orker can share the daemon: compare with `orkctl orker list` and remove a dead identity's by its label ([deploy guide](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#what-removes-a-tasks-container)).
- The run page shows when the run finished, and a task's panel shows when the task finished, with the date when it is not the day it started.
- The run page has an Edit button that opens the editor on the run's version.
- A child run now names the root run of its composed chain as well as its parent: `origin.rootRunId` in `GetRun`, `ListRuns` and archived runs, a `Root run:` line on `orkctl run get`, and a **Root run** link on the run page when it is not the parent. `ListRuns` and `orkctl run list` take `--filter origin.root_run_id=ID`, which lists every run below that root but not the root itself, and the run page of a top-level run that composes links that list as **Chain runs**. The engine registers one more search attribute at boot, `OrkflowOriginRootRunId`, and a cluster that refuses it still boots and warns ([UI_CLI_PARITY.md](https://github.com/orkstack/orkstack/blob/main/docs/UI_CLI_PARITY.md#run-origin)).
- `orkctl run get` now has a `TASK VALUES` table showing what each task returned, up to 64 characters of its JSON and at most 50 tasks. A longer value is cut, and a value over 4 KiB is not fetched; each names the command that saves it. `--tree` adds the table under each child run, and `--expand` adds one for a fan-out's items, reading up to 50 of them from the store. Terminal control characters are escaped, and `--json` is unchanged. A script that reads the human output sees one more table; use `--json`. [Reading runs](https://github.com/orkstack/orkstack/blob/main/docs/UI_CLI_PARITY.md#reading-runs)
- The Schedules tab can edit a schedule: its version pin, times, overlap policy, input and description, as `orkctl schedule update` can. It keeps the schedule's id, fires and pause. See [Orkflow schedules](https://github.com/orkstack/orkstack/blob/main/docs/ORKFLOW_SCHEDULES.md).

### Changed

- **BREAKING** The object store's keys have no default any more, so an instance or pod role can sign. With `ORK_S3_ACCESS_KEY` and `ORK_S3_SECRET_KEY` unset, `ork` and an `orker` on the `s3` backend use the AWS SDK's default credential chain, and a boot with nothing to sign with stops and says so. One key alone, or a session token with no key, also stops the boot. A deployment that relied on the old fallback to the development key `orkstack` must now set both keys; the quickstart, `make up` and `make run-ork` set them already, so they need nothing. A role can reach tasks through the host's instance metadata service, so close that path before using one. See [The object store's credentials](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#the-object-stores-credentials).
- New run ids are `ork-` and a UUIDv7 in lowercase base32, 30 characters, such as `ork-01m6qt8vete0691h2jn074a2yk`. Existing runs keep their ids and both shapes stay valid. A run id is opaque, so nothing should parse it; update a script that matched the older shape ([AGENTS.md](https://github.com/orkstack/orkstack/blob/main/AGENTS.md#7-orkflow-execution-model)).
- **BREAKING** An Orkflow that pins no `version:` now gets a UUIDv7 in lowercase base32 at its first apply, instead of the sha256 of its source. Re-applying an unchanged file still writes nothing, and versions already stored as hashes stay valid. Validating or planning a file that was never applied now reports no version and no definition digest, so a script that read them from `orkctl orkflow validate --json` or `orkctl run plan --file --json` must read them from the apply. Upgrade `orkctl` with the engine: an older `orkctl apply <dir>` reports such a file as stored with different source ([DSL.md](https://github.com/orkstack/orkstack/blob/main/docs/DSL.md#version)).
- The quickstart's object store now checks its keys and refuses an upload to a bucket that does not exist, as a production store does. A client of it other than `ork` and `orker`, such as `curl` or the AWS CLI, must sign with the keys in `compose.yaml`, and `docker compose up -d` applies this to your existing volume.
- `orkctl orker list` and `orkctl pool list --help` now say that an Orker which stopped stays listed and counted for up to 90 seconds, which is why an Orker restarted under another id reads as one too many until then. Set `ORK_ORKER_ID` to keep its id ([TROUBLESHOOTING.md](https://github.com/orkstack/orkstack/blob/main/docs/TROUBLESHOOTING.md)).
- Each page of the UI now has exactly one command-line icon, in its header, listing all of that page's commands, and Schedules, Triggers, Retention, Image policy, Operate and Apply gained one; a row's or a dialog's own command stays beside it. The panel now keeps its whole command in view wherever its icon stands: it could be clipped inside a table or off the screen ([UI_CLI_PARITY.md](https://github.com/orkstack/orkstack/blob/main/docs/UI_CLI_PARITY.md)).
- The run page opens a selected task's details and log directly under its row. The run's inputs and outputs now sit between the graph and the Tasks card, and the panels about one task (Image, What it waits for, Seen before) sit on that task. The side panels keep what is about the run: Why it failed, How it failed, Task map and Since the last run.
- A timeline row now gives a short word for why a task ended, such as `condition false`, and the whole reason appears as Reason on the task's panel. An unpinned row no longer names its Orker by default; the panel does, and **Show Orkers** in the Tasks card's More names it on every row.
- The run page's version plate links to that version on the Orkflow's page instead of listing the Orkflow's versions, which are on its Versions tab.
- The reason `orkctl orkflow compat` and the promote gate give for an Orkflow with no `outputs:` now says "the values of the tasks no other task needs" instead of "leaf task". Only the sentence changed: a script should read the verdict and the change kind, and one that matched the old words must match the new ones.
- A `PIN_TIMEOUT` failure's message now says the pin closed when it reached its lifetime, where it named an internal mechanism, and a `PIN_HOST_LOST` failure's message says the pin lost contact with the Orker hosting it, which may be gone or only unreachable, where it said the pin lost that Orker. The reason codes are unchanged, so match the code, not the message ([error reasons](https://github.com/orkstack/orkstack/blob/main/docs/REASONS.md)).
- An error `ListRuns`, `GetStats`, `SubmitRun`'s `max_running` check or `orkctl release` answers when the cluster's run index cannot be read, or not to its end, now speaks of that index and no longer carries the cluster's query or the names of its indexed fields. The status codes are unchanged ([DEPLOY.md](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md)).
- When submit or `orkctl pool list` cannot ask the cluster whether a pool has live Orkers, the error now reads `could not check pool "<pool>" for live Orkers: asking the cluster failed (<cause>); retry the request`, where it read `cannot tell whether pool "<pool>" has live Orkers: <cause>`. The status code is still `unavailable`; a script or alert that matched the old words must match the new ones ([TROUBLESHOOTING.md](https://github.com/orkstack/orkstack/blob/main/docs/TROUBLESHOOTING.md#could-not-check-pool--for-live-orkers)).
- Three messages now say what was not recorded instead of "unknown". A `RUN_STATE_CORRUPT` failure with no recorded cause reads `failed verification (no error was recorded)`, where it read `(unknown)`. `orkctl run get --tree` prints `unavailable (no answer: <message>)` for a child it could not read because no server answered, where it printed `unknown` as the code. An automation plan's note for a hold with no recorded start reads `on hold since a time the registry did not record`, where it read `an unknown time`. The reason codes are unchanged, so match the code, not the message ([error reasons](https://github.com/orkstack/orkstack/blob/main/docs/REASONS.md)).
- **BREAKING** `ork` and `orker` no longer start on a `--config` file, an `ORK_TELEMETRY_SINKS` or an `ORK_ACTIVITY_CATALOG` holding a second YAML document, which used to be ignored without a word, even when it did not parse. The refusal names the file or the setting and the line. Before upgrading, check each for a `---` after the first document: merge what follows into the first document or delete it, a trailing `---` included ([DEPLOY.md](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#1-configuration)).
- **BREAKING** An Orkflow file with a second YAML document is now refused, naming the file and the line it begins on, where everything after the first document used to be ignored without a word, even text that did not parse. To apply such a file, move each document to a file of its own, or delete what follows the first, a trailing `---` included. An automation document or an activity interface was already refused, and now says the line too. A version already stored keeps running, and only a new apply of its source is refused ([DSL.md](https://github.com/orkstack/orkstack/blob/main/docs/DSL.md)).
- A version an Orkflow was given rather than pinned now shows in a short form on every page: the first 8 characters of a 64-hex one, `…` and the last 7 of a UUIDv7 one. The full value is in the tooltip, URLs and `orkctl` commands, which need it, because the engine takes no short form.
- Admin → Namespaces fits the page without scrolling sideways: Signed by, Budget, Allowed secrets and Updated move to a page of each namespace's own, `/admin/namespaces/<name>`, which also holds its edit form. A namespace's name opens it; there is no Edit button.
- A webhook's id, a trigger's id and a schedule's name now open that row's edit, at an address you can link to (`?edit=ID`), in place of their Edit button. A schedule's fires stay behind Show fires.
- **Delete Orkflow** moved from the Versions tab to the More menu in the Orkflow's header, on every tab, and it now asks you to type the name.
- The UI uses the whole width of a wider monitor: the 1480 px cap on the content column is gone, so tables, the Dashboard, the run page's graph and timeline and the editor fill the window, while running text and forms keep a readable width.
- The run page's output card is now always titled `Outputs`, with a small tag saying whether the Orkflow declares them; the tag explains the undeclared case in plain words.
- An awaited task's panel on the run page now shows the values it was resolved with, by the UI, `orkctl` or a callback alike. A long value stays closed until you open it, and a value over 4 KiB is read only then, showing at most its first 64 KiB.
- The Dashboard is reorganised: the counts, Running now, Recent failures beside Pool health, then the last 7 days' charts. The Operate overview shows this deployment's facts and no longer lists the sidebar's pages. A page no longer repeats its namespace, which the breadcrumb names.
- On the Orkflows list, labels sit under the name and description, and the Labels and Tasks columns are gone. On Runs and on the Dashboard, a run's version sits under its Orkflow's name.

### Fixed

- A release now says which commit it came from: `orkctl version` printed `commit: unknown` on every published binary and image, and now prints the whole commit. `ork --version` and `orker --version` are new and print the same, without reading any configuration, including from the release images. Nothing to do. See https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md.
- A container stopped by its daemon shutting down or restarting, or by someone through the runtime, now fails `CONTAINER_STOPPED_BY_RUNTIME`, an infrastructure failure retried under the task's `retry:`, instead of `CONTAINER_EXIT_NONZERO` or, if its handler exited 0, a success or `VALUES_MISSING`. Its output is not committed. A workload that exits 143 by itself stays `CONTAINER_EXIT_NONZERO`. Behind the docker CLI against Podman's Docker-compatible socket, a kill through the engine is told apart and a stop may or may not be, so there an end with neither heard, the workload's own exit included, says that whether the workload exited on its own or the runtime stopped it is unknown ([OCI_ACTIVITY_CONTRACT.md](https://github.com/orkstack/orkstack/blob/main/docs/OCI_ACTIVITY_CONTRACT.md#82-reason-codes)). Match the new reason wherever you match reasons ([error reasons](https://github.com/orkstack/orkstack/blob/main/docs/REASONS.md)).
- A brief Temporal outage no longer ends a running task. It used to end one after a single `orker.heartbeat_interval` (5 s by default), failing it with a bare `context canceled` and stopping its container. Now a container runs on until nothing has answered its heartbeat for the 30 s heartbeat timeout, and a cancel recorded meanwhile still reaches it. Past that the Orker stops the container, and the task fails with a retryable infrastructure error, `ORKER_HEARTBEAT_TIMEOUT`, or `ORKER_HEARTBEAT_LOST` if the cluster answers first; the attempt's record says `ORKER_HEARTBEAT_LOST`. An open pin rides out 24 s, then fails `PIN_HOST_LOST`. `orker.heartbeat_interval` now only sets how fast a cancel arrives, so there is no longer a reason to raise it for a flaky frontend. See [Heartbeats and cancellation](https://github.com/orkstack/orkstack/blob/main/docs/OCI_ACTIVITY_CONTRACT.md#63-heartbeats-and-cancellation).
- An Orker with no declared capacity now tries again every 30 seconds to remove a container it could not remove, instead of leaving it until its next boot: one the daemon refused to remove, one a daemon restart left (still running under `live-restore`), and one a boot could not reap. It also removes a container the daemon finished creating after the CLI gave up. There is nothing to do. A host whose Orker never returns, or returns under another `ORK_ORKER_ID`, still needs an operator to remove its containers and attempt directories ([DEPLOY.md, "What removes a task's container"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#what-removes-a-tasks-container)).
- An Orker's boot no longer removes the pin directories and the upload and staging scratch of another Orker sharing its work root. It removes only its own identity's: a pin's lease now names its Orker, and scratch moves to `ork-spool/<owner>/` and `ork-stage/<owner>/`. A pin directory from before this release waits for its lease to expire; a file directly under `ork-spool/` or `ork-stage/` from before it stays, and the boot logs it, so remove those once no older Orker uses the work root. See [What removes a task's container](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#what-removes-a-tasks-container).
- `orkctl run logs -f` now resumes after the last chunk it printed when the engine replica serving it exits, bounded as `orkctl run watch` is, and each resume is said on stderr. No line is printed twice or skipped, and a try that ended during the outage is printed whole before the next ([DEPLOY.md](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md)).
- `orkctl run watch` no longer stops when the engine replica serving it exits. A connection that ends partway through a stream is resumed after the last event printed, on whichever replica answers, as `unavailable` already was. A replica told to stop used to end the watch with `Run ... finished with status RUNNING` and exit 0. It now ends its streams with `unavailable`, so every `orkctl` resumes, older ones included, and `orkctl` also resumes any clean end on a run still going. An interrupted `orkctl run logs` also no longer gets a clean end from a stopping replica, or a false end of the log. An error the engine itself reports still ends the watch ([DEPLOY.md](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md)).
- A webhook delivery's details open from the keyboard, from its time, as well as by clicking the row.
- A run whose task values nest more than about 50 levels deep no longer fails to open on the run page.
- The sidebar's `N running` count now follows a run that ends within seconds instead of lingering for up to 30.
- `ListRuns` with an `origin.id` filter longer than any origin's id can be now answers `invalid_argument`, naming the filter, instead of `internal` (or an empty list beside an `origin.root_run_id` filter), on a deployment with a run archive ([API.md](https://github.com/orkstack/orkstack/blob/main/docs/API.md)).

### Security

- An Orker's boot now removes the attempt directories its killed predecessor under the same `ORK_ORKER_ID` left under its work root, including the secret values staged in them in plain files. It never touches another identity's. A directory left by a release before this one names no identity and stays: remove those by hand, and those of an Orker that will not return ([deploy guide](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#what-removes-a-tasks-container)).
- The web UI's content security policy no longer allows `'unsafe-eval'`, so a script injected into the page cannot evaluate code. The YAML editor's schema checks are now compiled when the UI is built. If your gateway rewrites or adds a content security policy for the UI, you can drop `'unsafe-eval'` from it ([SECURITY_MODEL.md, "Transport, listeners and configuration"](https://github.com/orkstack/orkstack/blob/main/docs/SECURITY_MODEL.md#transport-listeners-and-configuration)).
- `orkctl run get`'s one-line input and output summaries, every error line `orkctl` prints for a run, a task, an attempt or a fan-out item, a schedule's `Input` line, a run's origin (its id, description, root run and reference) in `run get` and `run list`, and the values and `config.json` that `orkctl task run` prints now write a control or format character as an escape, so a value a task or an input holds cannot act on a terminal. `--json` prints what it did, and `task run --keep` keeps the file's bytes.
- `orkctl`'s remaining `--json` output (`webhook`, `run timing`, `version`, `run evidence`, `run logs`, `run inspect --watch`, `activity test`, `task run`) and its config file now write DEL, a C1 control and a format character, such as a bidirectional override or a zero-width character, as a JSON escape, as other `--json` output already did, so a hostile value cannot act on a terminal. It is the same JSON and needs nothing from a script that parses it; one that compares bytes sees `\u202e` where the raw character stood. `run evidence export --json` differs from the bundle's `MANIFEST.json` byte for byte only in that case.

## [0.2.0] - 2026-11-05

### Added

- An Orker now cordons itself during an object storage outage, so tasks wait in the pool instead of using up their retries, and resumes by itself once the store answers; `ORK_ORKER_STORE_CHECK_ENABLED=false` turns it off. `cordoned` is true for either cause while `cordon_reason` stays the operator's alone, so a client that shows why an Orker is cordoned should also read `ListOrkers`' new `store_outage` ([DEPLOY.md, "When object storage goes away"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#when-object-storage-goes-away)).
- `orkctl stats --by day` and `--by hour` count the runs created per day or per hour on your own calendar, and `GetStats` takes `bucket_width`, `timezone` and `bucket_count` for the same series ([CLI.md, "`orkctl stats`"](https://github.com/orkstack/orkstack/blob/main/docs/CLI.md#orkctl-stats)).
- A task waiting on a pool whose every Orker is at its declared capacity now says so, on the run page, in `orkctl run inspect` and in `InspectRun`'s `LiveAttempt.capacity_wait`. With metrics on, an Orker that declares a capacity also reports `ork.orker.capacity.*` and `ork.orker.admission.*`, and one that declares none logs at boot that its admission is best effort ([DEPLOY.md, "Declaring an Orker's capacity"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#declaring-an-orkers-capacity)).
- A canceled run shows who canceled it: the name your gateway asserted in `Ork-Principal` (`ORK_PRINCIPAL` for `orkctl`), as `canceled_by` in the API, in `orkctl run get` and `run list` and on the run page, always marked asserted and never authenticated. A cancel without the header, and a run canceled before this release, show no name.
- Activity images can carry an icon and descriptions of themselves, their ops and their keys: add `icon:` and `description:` to `interface.ork.yaml` and build with this release's `orkctl`, because an earlier one refuses those keys ([ACTIVITY_IMAGES.md, "Describing the activity"](https://github.com/orkstack/orkstack/blob/main/docs/ACTIVITY_IMAGES.md#describing-the-activity)). `orkctl activity inspect`, `ListActivities` and `InspectActivity` show them, and `InspectActivity` can answer a reference pinned by digest from an earlier read (`allow_cached`).
- `orkctl activity test` now reports the `with:` interface an image declares (declared, none or malformed), in its table and in `--json`; it never changes the verdict.
- The image policy also verifies cosign 3's default signature format, a Sigstore bundle stored as an OCI referrer, beside the legacy `.sig` layout, so you can sign your own images with cosign 2 or 3 ([DEPLOY.md, "Image supply-chain policy"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#image-supply-chain-policy)).
- Each release's page now ends with every image's digest and the commands that verify them, and the release attaches `SHA256SUMS.sigstore.json`, cosign's bundle of the checksum signature, beside `SHA256SUMS.sig` ([UPGRADING.md, "Release artifacts"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#release-artifacts)).
- The API listener now bounds what a client may make it hold: 64 KiB of headers (`431` above that), sent within 10 s over HTTP/1.1, `ORK_HTTP_IDLE_TIMEOUT` (15 minutes) for an idle connection, and `ORK_REQUEST_MAX_BYTES` for one Connect message (`resource_exhausted` above it). Unset, that cap follows the task ceiling, and a value set below that is refused at boot; the admin listener has the same kinds of bound ([DEPLOY.md, "The API listener's bounds"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#the-api-listeners-bounds)).

### Changed

- **BREAKING** No secret floor admits an Orker's own sources any more, an empty `ORK_ORKER_SECRET_ALLOW` included: a task that names one (such as `env:ORK_*`, `env:OTEL_*`, `env:AWS_*`, `file:/proc/...`, `file:/run/secrets/...`, or a file under its work root, the temp directory when `ORK_ORKER_WORKDIR` is unset) fails `SECRET_NOT_PERMITTED`, and a floor entry that can match only such sources stops the Orker at boot. Before you upgrade, give each such task a source of its own, set `ORK_ORKER_SECRET_ALLOW` on every Orker to exactly those sources, and drop any such entry ([UPGRADING.md, "The Orker's secret floor"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#the-orkers-secret-floor)).
- **BREAKING** A `file:` secret source must be a plain absolute path, with no `..`, `.` or empty segment, of at most 4096 bytes, under every floor, the empty one included; any other name fails `SECRET_NOT_PERMITTED`. Write each such source's path out plainly ([UPGRADING.md, "`file:` secret sources"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#file-secret-sources)).
- **BREAKING** The API listener now answers `403` to a request whose `Host` it does not admit, which stops DNS rebinding through a public name. Set `ORK_ALLOWED_HOSTS` on every `ork` to each name with a dot the engine is reached by; an IP address, `localhost`, a name with no dot and the host `ORK_HTTP_ADDR` names need nothing ([UPGRADING.md, "Allowed hosts"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#allowed-hosts)).
- **BREAKING** The admin listener (`ORK_ADMIN_ADDR`, on `ork` and `orker`) applies the same rule. List in `ORK_ADMIN_ALLOWED_HOSTS` each name with a dot a scraper dials, such as a Prometheus static target `host.docker.internal` or a Kubernetes Service FQDN; a scraper that dials an IP address needs nothing ([UPGRADING.md, "Allowed hosts"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#allowed-hosts)).
- **BREAKING** The release signs its images and `SHA256SUMS` in cosign 3's bundle format, which an engine or Orker of v0.1.0 cannot read: where a run's namespace requires a signer, a v0.1.0 Orker still polling refuses its bundle-signed images with `IMAGE_NOT_SIGNED`, which is never retried. Upgrade the Orkers with the engines; a deployment that stays on v0.1.0 is unaffected by this release, which leaves the `0.1` tag its catalog names on v0.1.0's images ([UPGRADING.md, "Release artifacts"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#release-artifacts)).
- **BREAKING** The Temporal Go SDK 1.50 records a marker in a run's history the first time one cancellation reaches more than one of its open scopes, which an engine of 0.1.0 cannot replay, so on a rollback or in a fleet that mixes releases such a run stays `RUNNING` (`unknown SDK flag: 9`) until an engine of 0.2.0 picks it up. With versioning on, roll back as before; with versioning off, roll back below 0.2.0 only when no run is open, and replace every engine replica together when rolling forward ([DEPLOY.md, "4. Rolling back"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#4-rolling-back)).
- **BREAKING** Every first-party activity image now ships jq 1.8 (was 1.7) and BusyBox 1.37, the `git` image git 2.54 and the `http` image curl 8.23, and jq 1.8 changes what some filters compute in a `json` task and in any `jq` a `shell` task runs. Check those filters and commands before you next apply their Orkflows ([UPGRADING.md, "jq 1.8 in the first-party images"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#jq-18-in-the-first-party-images)).
- **BREAKING** The `template` image now renders with gomplate 5.3.1 (was 4.3.3), which removed most of the names gomplate 4 served with a deprecation warning, so a template that calls one fails to render. Replace them, and check any `GOMPLATE_CONFIG` file and `AWS_META_ENDPOINT` setting, before you next apply those Orkflows ([UPGRADING.md, "gomplate 5 in the `template` image"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#gomplate-5-in-the-template-image)).
- **BREAKING** The Orker's boot probe now runs `docker.io/library/alpine:3.24` by digest (was alpine 3.20), and an Orker that cannot pull it refuses to start with `BIND_PROBE_IMAGE_UNAVAILABLE`. On an air-gapped or rate-limited host, mirror or load it before you upgrade ([UPGRADING.md, "One release at a time"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#one-release-at-a-time)).
- **BREAKING** An Orkflow whose `retry:` sets a negative `initial_interval_seconds` or `maximum_interval_seconds`, a `maximum_interval_seconds` below its `initial_interval_seconds`, or a `backoff_coefficient` that is set below 1 or not finite is now refused by validate, apply and plan, whatever its `maximum_attempts`. Fix the document before you next apply it; a version applied earlier keeps starting, with the nearest policy the cluster accepts ([UPGRADING.md, "Upgrading Orkflows with the release"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#upgrading-orkflows-with-the-release)).
- `uses: shell` and the other first-party names now resolve to the activity images' `0.2` tag when an Orkflow is applied, and a version already applied keeps the image it pinned. A host that mirrors the images needs the `0.2` images before that apply ([UPGRADING.md, "Upgrading from 0.1.0 to 0.2.0"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#upgrading-from-010-to-020)).
- A `retry:` that sets no `maximum_interval_seconds` now waits at most 60 seconds between attempts, not 100, in runs submitted from this release on. Set `maximum_interval_seconds: 100` to keep the old spacing ([UPGRADING.md, "Defaults that moved"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#defaults-that-moved)).
- Where the cluster has fair dispatch enabled, a run's requests for a pin host are now ordered by namespace as its tasks are, for runs submitted from this release on ([DEPLOY.md, "Fair dispatch across namespaces"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#fair-dispatch-across-namespaces)).
- An unknown key in an Orkflow or an activity interface is now refused in the document's own words, naming the key, where it stands and the keys allowed there (`line 10: unknown key "need" in tasks[1] of the Orkflow; allowed: …`). A script that matches the old sentence, which named an internal type, needs updating.
- Connect 1.21 gives some broken connections a different code, `canceled` or `internal` where a client saw `unavailable`, `invalid_argument` or `unknown`, and `orkctl run watch` and `run inspect --watch` now resume on a `canceled` they did not cause. A client that switches on these codes should check them ([UPGRADING.md, "Connect 1.21's error codes"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#connect-121s-error-codes)).
- The Temporal SDK's `temporal_activity_execution_failed` and `temporal_local_activity_execution_failed` metrics now carry a `failure_reason` attribute, and `temporal_sticky_cache_total_forced_eviction` no longer counts a worker's shutdown. A dashboard built on them may need adjusting.
- `CancelRun` now answers `UNAVAILABLE` or `RESOURCE_EXHAUSTED` when the cluster could not take the cancellation, and `CANCELED` or `DEADLINE_EXCEEDED` when the caller gave up first, instead of `INTERNAL`. A client may retry the first two.
- The web UI has a new design.
- The web UI's Runs page now opens with the last day's counts, which filter the list, and the last 7 days' outcomes, failures and flakiest tasks; a run page shows what changed since the last run, keeps one log and one card on the task you select, and lets you pause its updates without losing any; and the Orkflow editor shows the docs of the activity under the caret. A run page's `view=` parameter is gone, and in the UI cancelling a run asks for a reason and cordoning an Orker needs one.
- Every example in `examples/` now runs as it stands, with no inputs, given internet access, with three exceptions: `order-saga` and `approval-gate` still need `notify-block` stored first, and `custom-image` is now a recipe beside its build, gone from the Apply page's gallery. A store keeps any older version it holds, and if you adapted an example or submit one with your own inputs, some inputs and defaults changed ([UPGRADING.md, "The examples"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#the-examples)).
- The quickstart's Orker is now a pin host, one pin at a time, so an Orkflow with a pin runs on it with no setting of yours, and the quickstart runs Temporal's development server 1.9.1 and SeaweedFS 4.51.

### Removed

- Ten older examples are gone from `examples/` and from the Apply page's gallery: `advanced-demo`, `awaited-approval`, `branch-and-recover`, `cached-pipeline`, `composed-release`, `file-read`, `hello`, `pinned-build`, `release-block` and `shell-eval`. An Orkflow a deployment already stored from one of them is unaffected; for a new one, start from a [current example](https://github.com/orkstack/orkstack/blob/main/examples/README.md).

### Fixed

- A failed task's `error.message` now says the Orker's sentence once; it used to repeat it after the failure's category, usually marked `retryable: true` whatever the failure's own `retryable` said. A script that matches the repeated part needs updating.
- The quickstart's first start no longer stops with the Orker exited on a `403 AccessDenied`, which about half of first starts from clean volumes did. Running `docker compose up` twice is no longer needed.
- An Orker that cannot use its object store at boot now stops with the new `COMMIT_STORE_UNAVAILABLE` and the store's own answer; `COMMIT_STORE_NOT_CONDITIONAL` now means the store answered and cannot do conditional writes. An alert on the old reason for these causes needs the new one too ([REASONS.md](https://github.com/orkstack/orkstack/blob/main/docs/REASONS.md)).
- `GetStats` and `orkctl stats` no longer count a run twice, once as finished and once as running, in the moment after it ends.
- An Orker's own policy checks (its cpu and memory caps, secret schemes and `ORK_ORKER_SECRET_ALLOW` floor) now run after commit adoption and the memo step, so a retry another Orker already committed, or a cached task whose memo hits, no longer fails on an Orker with narrower settings. `RUN_AS_ORKER_UNAVAILABLE` is now raised with them, before secrets are staged and the image is pulled.
- `orkctl task run --secret NAME=file:PATH` now says why a file cannot be used, as the file system gave it, rather than calling every such file missing.
- The Orker's boot probe no longer leaves `ork-bindprobe-*` or `ork-sigprobe-*` containers behind when its boot is stopped or refused. One it could not remove, because it was killed first, carries the `ork.orker` label and is reaped by the next boot under the same identity.
- A task whose `retry:` sets an `initial_interval_seconds` above the default maximum interval, and no `maximum_interval_seconds`, no longer leaves its run stuck. On a deployment with versioning, a run v0.1.0 already left stuck stays on v0.1.0 and never gets the fix: cancel it, and terminate it if it stays running ([UPGRADING.md, "Upgrading Orkflows with the release"](https://github.com/orkstack/orkstack/blob/main/docs/UPGRADING.md#upgrading-orkflows-with-the-release)).
- Numbers a run used without publishing an event, because object storage refused its record, are now said rather than skipped, and a refused `RUN_CREATED` is written again under its number, so a stream no longer silently begins at sequence 2. Check any client that switches on event types for the new `STREAM_GAP`, which changes no run or task, and on errors for the `DataLoss` a read of the archive over such numbers ends with ([DEPLOY.md, "6. Replay safety across versions"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#6-replay-safety-across-versions)).
- A finished run that did not archive itself, because it was terminated from outside or object storage refused its ending, now gets an archive from a sweep on every `ork` replica instead of disappearing when the cluster's retention expires it. It is still lost if object storage is down at every pass until then, so alert on the new metric `ork.archive.sweep.unconfirmed` ([DEPLOY.md, "Retention cleanup and bucket lifecycle rules"](https://github.com/orkstack/orkstack/blob/main/docs/DEPLOY.md#retention-cleanup-and-bucket-lifecycle-rules)).

### Security

- Text an image or a registry supplies, in an image's `interface_error`, a resolution error or a signature check's refusal, is now escaped and cut at 512 bytes, and `orkctl --json` of commands such as `run get`, `run list`, `activity inspect` and `activity list` writes DEL, every C1 control and every format character as a `\u` escape, so neither can drive your terminal. The `--json` output decodes to the same values.
- The web UI's page is now sent under a strict content security policy, which the engine sends as a header: scripts run only from the page's own origin, inline ones only when the policy names their hash, and `eval` only for the YAML editor's schema checks. A script a proxy injects into the page is now blocked.
- The first-party activity images move to Alpine 3.24; Alpine 3.20, their base until now, is past its support window.
- The `template` image still carries go-jose v4.1.4 (GHSA-mgcc-cww5-fp2q, high, fixed in v4.1.6) inside gomplate 5.3.1, gomplate's latest release. There is nothing to do; it moves when gomplate releases with the fix ([the image's README](https://github.com/orkstack/orkstack/blob/main/images/activity-template/README.md)).
